# Конспект: CI/CD на практике

## Что мы построили

Учебный проект: Flask-приложение с эндпоинтом `/health`, обёрнутое в Docker, с полностью автоматическим пайплайном через GitHub Actions.

**Цепочка при каждом `git push` в main:**
```
push → checkout код → установка Python → установка зависимостей 
→ запуск тестов → (если тесты прошли) → логин в Docker Hub 
→ сборка образа → публикация образа
```

---

## Ключевые термины

| Термин | Что значит |
|---|---|
| **CI** (Continuous Integration) | Автоматическая проверка кода (тесты) при каждом изменении |
| **CD** (Continuous Deployment/Delivery) | Автоматическая сборка и публикация готового артефакта после успешного CI |
| **Pipeline** | Общее понятие: последовательность автоматизированных этапов обработки кода |
| **Workflow** | Конкретная реализация pipeline в GitHub Actions — файл `.yml` |
| **Job** | Задача внутри workflow (набор шагов, выполняемых на одной виртуальной машине) |
| **Step** | Один шаг внутри job — либо `uses` (готовый чужой блок), либо `run` (своя команда) |
| **Runner** | Виртуальная машина, на которой GitHub выполняет workflow (`ubuntu-latest` и т.д.) |
| **Secret** | Зашифрованная переменная (пароль/токен), недоступная в открытом виде в коде |
| **Token** | Строка, заменяющая пароль для доступа — с ограниченными правами и возможностью отзыва |

## Docker: базовые понятия

- **Образ (image)** — шаблон для контейнера, собирается из `Dockerfile`
- **Контейнер (container)** — запущенный экземпляр образа
- **Dockerfile** — инструкции для сборки образа (`FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`)
- **`0.0.0.0` vs `127.0.0.1`** — чтобы сервис внутри контейнера был доступен снаружи, Flask должен слушать `0.0.0.0`, а не `127.0.0.1`

## Git: минимальный рабочий цикл

```
Working Directory → (git add) → Staging Area → (git commit) → Repository
```

- `git add` — пометить изменения как готовые к коммиту
- `git commit` — зафиксировать снимок истории с сообщением
- `git push` — отправить локальные коммиты на GitHub
- `git pull` — забрать коммиты с GitHub в локальную историю

**Когда обязателен `pull` перед `push`:** если на GitHub есть коммиты, которых нет локально (например, кто-то другой уже запушил, или GitHub сам создал коммит при инициализации репозитория).

**Конфликт слияния (merge conflict):** возникает, если два человека изменили одну и ту же строку по-разному. Git помечает конфликт маркерами `<<<<<<<` / `=======` / `>>>>>>>` в файле — разрешается вручную, затем `add` + `commit` + `push`.

## GitHub Actions: структура workflow-файла

Расположение: `.github/workflows/имя.yml`

```yaml
name: CI                    # название пайплайна

on:
  push:
    branches: [main]        # триггер — когда запускать

jobs:
  test:
    runs-on: ubuntu-latest  # на чём выполнять
    steps:
      - name: Checkout code
        uses: actions/checkout@v4        # готовый чужой блок

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: pip install -r requirements.txt   # своя команда

      - name: Run tests
        run: pytest

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/health-app:latest
```

**Важно:** если какой-то шаг завершается с ненулевым кодом выхода (например, тест провалился) — все последующие шаги в этом job не выполняются. Именно поэтому тесты стоят раньше сборки и публикации — это защищает от попадания сломанного кода в Docker Hub.

## Как это связано с DevSecOps (для собеседования)

- **Секреты не хранятся в коде** — используются GitHub Secrets вместо хардкода паролей
- **Shift left** — проверки (тесты, а в перспективе SAST/DAST) выполняются как можно раньше в процессе, а не после релиза
- **Автоматизация как защита** — пайплайн физически не даёт непроверенному коду попасть в публикацию
